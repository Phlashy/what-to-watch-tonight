## 4. Backend — correctness & data integrity

### BE-1 — `show-status` "finished/dropped" removes a title from _every_ list, not just watchlists ✅ (Medium)

- **Where:** `server/routes/show-status.js:42-43` — `DELETE FROM list_items WHERE title_id = ?`, fired once `noOneStillEngaged` is true.
- **Why it's wrong:** the gate (only remove when no one is still engaged) is correct and was the June fix, but the SQL itself is unscoped. For this family that includes curated/keep lists (`arianne_100_family`, `christmas`, `casey_brothers_recs`). Marking a show finished silently strips it from a curated 100-list, with no undo.
- **Failure scenario:** the last engaged viewer finishes a show that's on `arianne_100_family` → it vanishes from Arianne's curated list.
- **Fix:** scope the delete to the configured watchlist(s) (the context→lists map / `family_to_watch`), or tag lists "watchlist" vs "keep" and only prune watchlists. Add a regression test.
- **Effort:** S–M.

### BE-4 — Chat assistant's "today's date" is UTC, not Vancouver ✅ (Low, but against the house rule)

- **Where:** `server/routes/chat.js:58` — `Today's date: ${new Date().toISOString().split('T')[0]}`.
- **Why it's wrong:** UTC is a day ahead of Vancouver after ~17:00 local — i.e. exactly at movie-night o'clock — so the assistant can state tomorrow's date. Directly contradicts the documented "name the zone, `America/Vancouver`" convention. (`what-to-watch.js:23-25` has the same UTC pattern for the 12-month cutoff, but a 1-day skew on a 1-year window is immaterial — leave it.)
- **Fix:** format with `Intl.DateTimeFormat('en-CA', { timeZone: 'America/Vancouver' })`.
- **Effort:** S.

### BE-2 — `PUT /api/titles/:id`: 200-with-null on missing row; doesn't accept `content_rating`/`imdb_id` ✅ (Low)

- **Where:** `server/routes/titles.js` PUT handler (~161-207). The June pass added 404s for missing viewings/list-items/shortlists/collection; titles PUT was missed, so an UPDATE affecting 0 rows still `SELECT…get()`→`undefined`→`res.json(null)` with 200. Separately, POST accepts `content_rating`/`imdb_id` (lines 104-144) but PUT doesn't — so an in-app edit can't correct a wrong age certificate.
- **Fix:** 404 when the row doesn't exist; add `content_rating` and `imdb_id` to the PUT column set.
- **Effort:** S.

### BE-3 — TMDB proxy forwards upstream errors as HTTP 200 ✅ (Low)

- **Where:** `server/routes/tmdb.js` `/movie/:id`, `/tv/:id`, `/search` — `response.json()` without checking `response.ok`.
- **Why it's wrong:** a TMDB 404/401 body is passed to the client as a 200; `/search` on upstream failure returns `[]`, which the UI reads as "no results" rather than "TMDB is down." No key leak (the key is only in the request URL, never echoed).
- **Fix:** check `response.ok` and forward a 502/503 to the global handler on upstream failure.
- **Effort:** S.

### BE-M3 — Chat prompt-injection surface (informational — design is sound)

Tool results return family-authored free text (notes, tags, names) to the model. The only two _mutating_ tools (`add_to_list`/`remove_from_list`) are gated server-side by `confirmed:true`, set only from a real user "yes" in the latest message — the correct mitigation. All other tools are read-only. **No action — but don't weaken that gate** if the parked "Options" feature adds write-tools.

## 5. Frontend — correctness

### FE-1 — `api()` throws, but ~5 callers are written as if it returns a Response → errors silently vanish (High, systemic)

- **Where:** `client/src/api.js:34` throws on any non-OK response (the error carries `.status`/`.body`). But several callers do `const res = await api(...); if (res.ok) {…} else {…}` inside `try/finally` with **no `catch`** — so the `else` is dead code and the throw is swallowed with zero user feedback:
  - `pages/Lists.jsx:83` — create list; a duplicate-name 409 should show "Failed to create list" but the branch is dead → form just stops spinning, no error.
  - `components/EditListModal.jsx:58` — rename conflicts fail silently.
  - `pages/TitleDetail.jsx:169-178` — `addToCollection`; the "already has a Blu-ray entry" 409 confirm never appears.
  - `components/AddToListSheet.jsx:40` — adding a title already on a list throws; item isn't marked added.
  - `components/LogViewing.jsx:156` — a failed save (offline/500) is swallowed; the modal stays open with no indication whether it saved.
- **Correct exemplars to copy:** `components/QuickAdd.jsx:120-131` and `components/TMDBPicker.jsx:59` already use `catch (e) { if (e.status === 409) … else setError(e.message) }`.
- **Fix:** rewrite the five to the catch-the-throw style; treat 409 in `catch`, surface `e.message` otherwise. Consider a tiny shared `useAsyncAction`/toast helper so this can't recur (see `FE-6`).
- **Effort:** S–M. **Highest-value frontend fix.**

### FE-2 — `ViewingItem` collapsed view shows unsaved tags after Cancel (Medium)

- **Where:** `components/ViewingItem.jsx:345` renders the collapsed tag list from `draft.tags` while everything else reads `v.*`. `draft` is `useState`-initialized once; Cancel (`:277`) only does `setEditing(false)`, never resets `draft`. Add a tag → Cancel → the collapsed row shows the unsaved chip (not persisted; a refresh clears it). The component is keyed `v.id` and stays mounted across the parent's `loadTitle()`, so `draft` never re-syncs to an externally updated `v`.
- **Fix:** render the collapsed tags from `parseJSON(v.tags)`, and/or reset `draft` on Cancel.
- **Effort:** S.

### FE-3 — TitleDetail inline shortlist toggle is non-optimistic and uncaught (Low–Medium)

- **Where:** `pages/TitleDetail.jsx:102` awaits the POST then updates state, no `catch` — the star lags a round-trip and never updates on failure. `pages/WhatToWatch.jsx:87` does it right (optimistic + revert).
- **Fix:** mirror the optimistic pattern, or extract a shared `useShortlistToggle`.
- **Effort:** S.

### FE-4 — Search boxes have no request sequencing/abort (stale-result race) (Low–Medium)

- **Where:** `components/LogViewing.jsx:60-84` (two _sequential_ awaited fetches in a debounced effect) and `pages/Search.jsx:185-229` — in-flight requests aren't aborted, so a slow response for an old query can overwrite newer results. `QuickAdd.jsx:72-87` is the better model (`Promise.all` + per-call `.catch`).
- **Fix:** add an `AbortController`/"latest wins" guard; make LogViewing use `Promise.all`.
- **Effort:** S–M. (Low real-world harm on a LAN, but present in newer code.)

### FE-5 — `updateShowStatus` flips the whole page to its loading skeleton (Low)

- **Where:** `pages/TitleDetail.jsx:122-142` calls `loadTitle()` (which sets `loading=true`, swapping the whole page for the skeleton at `:286`) just to toggle one status chip — a jarring full-page flash.
- **Fix:** update show-status/list memberships in place (like `onUpdated`/`toggleShortlist`) instead of a full reload.
- **Effort:** S–M.

### FE-6 — Mutation-path errors still vanish generally (Medium — the root cause behind FE-1)

- The June "blank screen on load failure" fix covered _load_ paths (`FamilyContext` retry screen, `ErrorBoundary`, `ErrorState`). But _mutation_ handlers still swallow failures — beyond `FE-1`, also `updateAddedBy`, `removeFromCollection`, `deleteViewing`, `saveTitle` in TitleDetail; ~9 empty `catch(()=>{})` across the tree.
- **Fix:** a small shared `useAsyncAction`/toast helper the mutation handlers use uniformly — closes `FE-1` and this at once.
- **Effort:** M.

### FE-7 — LogViewing can save a viewing with no watchers and no confirmation (Low)

`components/LogViewing.jsx:134` only guards `!selectedTitleId`; an empty `people` list saves silently. Add a guard / confirmation. **S.**
